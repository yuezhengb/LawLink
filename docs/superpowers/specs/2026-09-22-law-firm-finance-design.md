# 律所经营财务闭环设计

日期：2026-09-22
状态：范围已确认，实施前书面复核
范围：LawLink 内部使用，不商业化，不替换现有外部财务老师的报税职责

## 1. 设计结论

参考 101 VPS 上正在运行的 `admin.sofos.cc` 财务工作区后，本项目不再按“导入银行流水并做一次分成计算”的小模块规划，而是建设一套嵌入 LawLink 的律所经营财务闭环：

```text
LawLink 业务事实
  客户 / 案件 / 合同 / Billing / Receivable / 已确认 Payment / 发票 / 分成方案
        ↓
财务资料与证据层
  银行 / 工资 / 外部财务表导入 → 原文件归档 → 标准化流水 → 来源证据
        ↓
对账与认领层
  自动匹配 → 待认领队列 → 人工确认 / 忽略 / 差异记录
        ↓
规则计算与持久化层
  案件来源档案 → 渠道/律所/律师分配 → 个人双余额 → 经营结果
        ↓
月结交付层
  计算批次 → 月度调整/冲销 → 工资表、台账包、个人透视和完整月结包
```

LawLink 仍然是案件、合同、应收、确认收款和业务权限的事实来源；新增财务域负责银行事实、来源证据、内部核算、个人结算和月结交付。财务域的派生结果不得反向改写案件原始事实。

本设计只借鉴现有系统已经验证过的业务边界和交互方式，不复制 101 VPS 上的源代码、数据库、客户资料或生产配置。若未来需要直接复用第三方代码，必须先单独核对许可证和依赖边界。

## 2. 背景与边界

### 2.1 已有能力

LawLink 当前已经具备以下可复用能力：

- 客户、案件、承办团队和案件可见性；
- 委托收费、合同金额、分期应收和补充协议；
- 待确认实收、确认收款、付款分配和发票关联；
- 律师分成方案、分成计提、实际结算和财务更正；
- 审批、角色权限、审计日志和私有附件。

这些能力适合作为“案件/合同侧子账”。当前模型还没有完整的会计科目、借贷凭证、银行总账、工资社保账和正式三表，因此不能把现有财务页面直接当作外账会计系统。

### 2.2 总目标

本项目交付一个可重复运行、可解释、可追溯的内部经营财务闭环：

1. 原始资料可归档、去重、追溯来源和重新处理；
2. 银行收款可与 LawLink 已确认收款、客户、项目和发票进行确定性勾稽；
3. 无法确定归属的收款和退款进入人工认领队列，不被系统强行分配；
4. 规则化计算渠道佣金、律所留成、案源/承办/协办分配和个人结算；
5. 分开呈现个人可分配收入、个人自担成本预存、合伙人税款资金和投资人资本流；
6. 每个账期输出人员、项目和律所经营三套核对视角，以及月度财务交付包；
7. 每一次计算都能回溯到来源批次、规则版本、计算批次、人工调整和操作者。

### 2.3 不做的事情

当前闭环不包含：

- 自动报税、税务申报或替代外部财务老师；
- 自动发放工资、缴纳社保、对外付款或银行开放接口；
- 将微信客户接单表直接同步为系统主数据；第一阶段只接受受控的脱敏导出或人工映射；
- 把系统输出称为法定资产负债表、利润表或现金流量表；外部三表只作为核对资料和草稿来源；
- 在 LawLink 内直接建立正式复式总账、会计凭证过账和期间结账锁账；
- 把真实客户接单表、银行流水、工资表、花名册或外部账表放入 Git、测试夹具、日志或公开下载地址。

客户接单表在获得可控的 XLSX/CSV 导出后再设计字段映射，不阻塞第一期的规则计算与对账。

### 2.4 分阶段交付

每一阶段都有独立的测试和验收结果，前一阶段稳定后才进入下一阶段：

| 阶段 | 交付重点 | 可验收结果 |
| --- | --- | --- |
| 0. 边界与底座 | 权限、私有存储、财务域模型、审计和合成数据 | 无真实数据也能完成安装、迁移和权限反向测试 |
| 1. 资料与对账 | 银行/工资/外部表导入、来源证据、去重、自动建议、待认领 | 一批合成流水可预览、提交、匹配、人工确认和导出 |
| 2. 分配与三视角 | 案件来源档案、版本化规则、分配快照、人员/项目/律所视角 | 已确认收款能生成守恒的不可变核算批次 |
| 3. 个人内账与经营 | 双余额、工资社保、报销/收入提取、合伙人税款、投资人资本 | 每名律师和律所经营结果可按月解释，资本不混入经营损益 |
| 4. 月结交付 | 持久化计算、来源哈希、追加调整/冲销、工资表/台账包/完整包 | 账期有阻断提示、可复核、可重生成且不改原始事实 |
| 后续独立项目 | 正式总账、法定报表、税务或 ERP 对接 | 以外部财务老师确认的会计口径另立设计，不提前绑定 |

阶段 1 和阶段 2 是最小可用闭环；阶段 3、4 是对照 `admin.sofos.cc` 实际工作方式补齐的生产可用能力。任何阶段都不直接连接生产数据库或导入真实客户数据作为开发验收。

## 3. 方案选择

### 3.1 选定方案：LawLink 内置财务域

优点是最大程度复用现有律所业务模型、权限和审计链，案件收入不会被另一个系统重新录入；适合本所内部使用，数据边界也最容易控制。

代价是需要自行补充复式记账、工资社保和正式报表能力，因此必须将“案件子账”和“会计总账”分开设计。

### 3.2 备选方案：LawLink 对接 ERPNext

[ERPNext](https://github.com/frappe/erpnext) 已提供会计、现金流、项目、工时和盈利分析等 ERP 能力，适合作为未来正式会计后台。它采用 GPL-3.0，若采用，应作为独立服务通过 API 对接，不将其代码直接复制进 MIT 授权的 LawLink 仓库。代价是部署、数据同步、权限映射和双系统排错成本明显增加。

### 3.3 其他参考系统

[Dolibarr](https://github.com/Dolibarr/dolibarr) 有客户、报价、发票、订单、费用和会计模块，较轻量，但律师分成和案件生命周期仍需大量适配。

[LedgerSMB](https://github.com/ledgersmb/LedgerSMB) 的复式记账、发票、项目和 PostgreSQL 财务核心较强，但其技术栈和业务模型与 LawLink 差异较大。

[Akaunting](https://github.com/akaunting/akaunting) 的功能形态接近小型企业财务，但当前仓库标注 BSL，不按严格开源系统作为本项目的基础依赖。

## 4. 系统架构

### 4.1 模块边界

继续使用 LawLink 的 Next.js 应用和 PostgreSQL，但财务新表、新服务和新页面按财务域隔离，不在案件页面散落计算逻辑。财务域分为来源证据、对账认领、规则计算、个人内账和月结交付五个边界清晰的单元。

```text
LawLink 业务域
  客户 / 案件 / 委托 / Billing / Receivable / FeeEntry / Payment
                         |
                         | 稳定业务 ID 与已确认事件
                         v
财务来源证据域
  导入批次 -> 原文件归档 -> 标准化流水 -> 来源指纹
                         |
                         v
财务对账与认领域
  匹配建议 -> 待认领队列 -> 人工确认/忽略 -> 退款与差异链
                         |
                         v
财务规则与内账域
  案件来源档案 -> 版本化分配 -> 个人双余额 -> 律所经营结果
                         |
                         v
月结交付域
  计算批次 -> 追加调整/冲销 -> 工资表/台账包/三视角导出
                         |
                         v
未来会计域
  科目 -> 凭证 -> 借贷分录 -> 期间结账 -> 三表
```

### 4.2 数据主权

- 案件、合同、案件应收和已确认案件收款仍以 LawLink 记录为准；
- 银行流水以导入批次和原始文件摘要为准，不覆盖原始文件；
- 规则计算结果是带版本的派生结果，不直接修改案件原始收款；
- 对账人工确认只能产生匹配关系或更正记录，不能删除原始流水；
- 未来正式会计凭证必须引用来源事件，不能绕过来源事件手工改余额。

### 4.3 关联键

第一期优先使用已有稳定 ID：`matterId`、`billingId`、`receivableId`、`feeEntryId`、`paymentId`、发票 ID 和导入批次/流水指纹。合同号、发票号和银行流水号只作为业务匹配字段，不能单独承担唯一身份。

### 4.4 核心财务模型

新模型按职责拆分，不把所有信息塞进一张“财务流水表”：

- `FinanceImportBatch`：导入类型、账期、文件摘要、状态、统计、操作者和失败原因；
- `FinanceSourceFile` / `FinanceSourceRow`：私有原文件元数据、标准化来源行、来源行号、原始字段摘要和去重指纹；
- `FinanceReconciliationCase`：银行行与 Payment/发票/费用/项目的候选、置信度、状态、理由和确认审计；
- `FinanceMatterProfile`：案件财务来源、参与人员、渠道标签和规则引用；
- `FinanceRuleSet` / `FinanceRuleVersion`：可配置比例、固定金额、适用范围、生效区间、舍入和发布审计；
- `FinanceCalculationRun`：账期、输入来源摘要、规则版本、`sourceHash`、状态、触发人和计算时间；
- `FinanceAllocationLine`：每一笔已确认收款的渠道、律所、案源、承办、协办和冻结明细；
- `FinancePersonLedgerEntry`：收入、成本、预存、预存使用、提取、税款预付和冻结款的追加式个人台账；
- `FinancePayrollFact`：工资、社保、公积金、个税、报销和实际支付期间的导入/核对事实；
- `FinancePartnerTaxRecord`：合伙人税款阶段、预计税额、律所预付、个人实缴和完税证据；
- `FinanceCapitalFlow`：投资人出资、退资、借款、代转人和关联银行流水；
- `FinanceAdjustment`：月度差额调整、原因、依据、目标科目、操作者和反向冲销链；
- `FinanceMonthlyClose` / `FinanceArtifact`：账期状态、阻断项、复核提示、生成文件和交付记录。

所有金额字段使用 Decimal 或最小货币单位，禁止用 JavaScript 浮点数作为持久化金额。原始事实和派生台账之间使用稳定外键或来源指纹关联，不复制完整客户敏感文本。

### 4.5 持久化计算原则

月结或内部账页面首次读取某一账期时，如果没有匹配当前来源的持久化结果，服务端生成一个计算批次；生成文件和报表只能引用该批次，不允许每个页面各自重算。

`sourceHash` 至少覆盖账期内及以前影响结果的人员规则、案件来源档案、已确认流水、工资事实、税款记录、资本流和已入账调整。来源变化后生成新批次，旧批次只读保留。

计算批次状态固定为：

- `PREVIEW`：可以查看阻断项和结果，但不进入正式报表；
- `COMMITTED`：输入摘要、规则版本和人工确认完整，可以被报表和交付文件引用；
- `SUPERSEDED`：有新批次替代，但保留原结果和审计；
- `FAILED`：记录失败原因，不产生半套正式结果。

## 5. 财务工作区与实施表面

### 5.1 资料导入

新增导入批次管理，主链支持 XLSX、XLS、CSV；PDF 先进入私有原文件归档，并通过独立解析适配层逐步支持文本提取和 OCR。OCR 失败不能阻塞人工上传结构化表，也不能凭低置信度结果自动入账。

每个批次保存：来源类型、文件摘要、账期、导入人、导入时间、行数、成功数、重复数和错误数。原始文件进入私有存储，日志和界面不输出完整身份证号、电话、银行卡号或客户敏感信息。

标准化流水至少包含：交易日期、金额、收支方向、对方摘要、用途摘要、账户标识、来源行号、原始批次和去重指纹。金额统一使用人民币分或 Decimal 规则处理，不使用浮点数。

### 5.2 对账工作台

匹配状态固定为：待匹配、系统建议、已确认、疑点、忽略。系统建议必须展示匹配依据，例如金额、日期窗口、流水号/发票引用、案件、合同和摘要；人工确认要记录操作者、时间和理由。

对账对象包括：

- 银行收款与 LawLink 已确认 `Payment`；
- 银行收款与发票/应收；
- 银行支出与费用、工资、社保、报销或合伙人往来；
- LawLink 收款与外部财务三表收入；
- 内部律师分配结果与实际支付/结算。

待确认的 LawLink 实收不能进入已收款对账结果，不能派生律师分成，沿用现有“先登记、后确认”的门禁。

退款或退费必须关联原始律师费收入，后续项目和个人视角使用净收入；银行支出、工资、社保、报销和合伙人往来必须进入明确的费用/个人/资本分类，不能被错误地当作待认领收入。

### 5.3 规则计算器

规则由规则集、适用范围、生效日期、失效日期、比例、固定金额、舍入方式和说明组成。规则一旦被计算批次使用，不允许原地修改，只能建立新版本。

初始规则模板覆盖：

- 渠道案件：渠道佣金、律所留存、律师分配池；
- 自拓案件：按合伙人、独立律师等身份配置律所提取比例；
- 协办律师或助理的分配；
- 工资、社保、报销、预支、借款和个人税费预留；
- 合伙人出资、垫款和律所经营成本的独立归类。

流程资料中的 20%/45%/35%、10% 和 15%—18%只作为初始规则模板，必须可配置并保留生效日期与来源说明；25%等税务口径也只作为参数，不在系统中固化为法律结论。

计算结果至少分为三种视图：

1. 外部经营账：收入、成本、现金、应收、应付、出资和借款；
2. 律所内部经营分配账：案件收入在渠道、律所、承办人和协办人之间的分配；
3. 律师个人结算账：可分配收入、工资/社保、报销、预支、税费预留和应结余额。

每次计算生成不可变快照，显示输入金额、规则版本、每一步扣减、舍入余数和最终结果。默认舍入余数归入律所留存，同时在明细中显式展示；若实际制度不同，通过规则配置调整。

个人内账必须把以下两条余额分开：

1. **可分配收入余额**：个人案件分配收入减去自担成本、未结案冻结款、收入提取和合伙人税款预付；
2. **自担成本预存余额**：律师本人或主任/律所代转、用于覆盖基础工资和个人承担社保公积金的预存资金。

每月计算预存使用、期末预存余额、未覆盖自担成本和至少两个月自担成本覆盖缺口；缺口允许跨月延续。收入提取不再重复作为律所经营成本，合伙人个人实际缴税不作为律所银行流水虚构记录。

律所经营结果使用管理内账口径：

```text
律师费收入 + 其他经营收入
- 渠道佣金应计 - 律师分成应计 - 流转税费
- 律所承担薪资 - 律所承担社保公积金 - 房租及办公成本
= 经营结果
```

投资人出资、退资、借款、个人自担预存、律师收入提取和合伙人个人税款资金不进入经营结果。

### 5.4 用户工作区与报表

财务入口按六组组织，避免把所有操作堆在一个页面：

1. **财务总览**：期间选择、银行余额、收入、成本、个人自担成本预警和经营结果；
2. **银行流水与归档**：上传、原文件归档、解析重处理、流水明细和来源证据；
3. **待办认领与归类**：待定挂账、自动重新匹配、人工关联客户/项目、退款关联、认领 Excel 往返；
4. **分成与个人内账**：律师提成与成本、个人双余额、合伙人税款、投资人经营和资本流；
5. **月结与财务交付**：银行资料覆盖、阻断项、人工调整/冲销、计算批次和月度文件；
6. **报表与核对**：人员透支、客户/项目归属、律所经营结果、逐层穿透和 Excel 导出。

当前报表是“核对报表”，不是法定报表，至少包括：

- 银行流水收支汇总；
- LawLink 收款、发票和应收汇总；
- 银行与 LawLink 的未匹配/金额差异；
- 按案件、律师、渠道和月份的内部分配；
- 工资、社保、报销、出资和垫款明细；
- 与外部三表的收入、成本和现金差异；
- 指定期间的规则计算快照和导出文件。

工资表、个人透视、台账包、调整审计表和完整月结包必须引用同一 `calculationRunId` 与 `sourceHash`，不允许导出器另算一套数字。

## 6. 权限、隐私与审计

- 读取财务明细、确认匹配、维护规则、确认更正和导出分别授权；
- 财务权限至少拆分为 `finance.read`、`finance.import`、`finance.reconcile`、`finance.rules`、`finance.adjust` 和 `finance.export`；
- 系统管理员身份不能自动取得业务财务确认权；沿用现有岗位与独立财务权限模型；
- 规则发布、导入、匹配确认、差异关闭、计算批次、人工调整、冲销和导出都写入审计；
- 审计日志不得保存完整银行账号、身份证号、电话和客户原始敏感文本；
- 原始财务文件只存私有附件，下载继续使用短期授权链接；
- 任何测试、演示和 CI 数据使用合成样本，不把真实客户接单表、银行流水或工资表提交 Git。

## 7. 异常处理

- 文件无法识别、字段缺失或金额格式错误：批次失败并逐行给出原因，不产生部分正式结果；
- 重复导入：依据文件摘要和行指纹识别，保留重复记录的审计结果，不重复计算；
- 自动匹配不确定：进入疑点队列，不自动确认；
- 规则缺失、比例重叠、比例超过上限或生效期冲突：阻止整批计算，不输出半成品结算结果；
- 原始收款、流水和外部账表不一致：创建差异项，通过更正或补充来源解决，不直接改原始记录；
- 计算后规则变化：旧快照保持原规则版本，新规则只能重新生成新批次；
- 任何更正使用追加记录，禁止物理删除已经参与对账或结算的来源数据。

差异诊断必须区分四类根因：

- **识别问题**：原文件或解析器没有读出字段；
- **存储问题**：来源有金额，但标准化或数据库没有正确保存；
- **计算问题**：来源和数据库正确，但规则或分配结果不一致；
- **展示问题**：持久化结果正确，页面汇总或格式错误。

每类问题要进入对应的重处理、补充来源、重建批次或页面修复路径，不能用一次“重新计算”掩盖来源或存储缺陷。

## 8. 验收标准

阶段 1、2 完成后，最小可用闭环必须满足：

1. 同一文件重复导入不会重复产生流水或分配结果；
2. 只有已确认的 LawLink 实收才能进入收款匹配和内部分配；
3. 每一笔分配都能回溯到案件、来源收款、规则版本和计算批次；
4. 所有差异都有状态、责任人、理由和关闭记录；
5. 规则变更不会改变历史计算快照；
6. 计算满足金额守恒、比例上限、非负余额和舍入可解释性；
7. 财务权限、敏感字段和私有文件下载通过正反向测试；
8. 使用合成样本完成银行流水、外部三表、案件收款和律师分配的端到端演练；
9. `npm run lint`、`npm run typecheck`、`npm run prisma:validate` 和 `npm run build` 通过；
10. 不执行生产数据库迁移、不导入真实客户接单表、不改变现有生产服务。

阶段 3、4 还必须满足：

11. 个人可分配收入与自担成本预存余额始终分离，并能显示两个月覆盖缺口；
12. 合伙人税款记录能区分律所预付与个人实缴，投资人资本流不进入经营结果；
13. 月度调整只新增凭证或反向凭证，历史银行、工资和已提交计算批次不被改写；
14. 工资表、个人透视、台账包和完整月结包引用同一 `calculationRunId` 与 `sourceHash`；
15. 至少完成一个脱敏账期的人工复核，得到用户和外部财务老师对口径的书面确认。

## 9. 后续阶段

内部经营闭环连续完成至少一个账期，并由外部财务老师确认科目和权责口径后，再单独设计正式会计域：会计科目、会计期间、凭证、借贷分录、法定三表和税务接口。届时评估自建总账、通过 API 对接 ERPNext 或 LedgerSMB；该阶段的许可证、数据同步和法定报表不提前混入当前实现。
