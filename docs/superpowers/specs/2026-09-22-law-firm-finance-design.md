# 律所内部财务系统第一期设计

日期：2026-09-22
状态：待用户审阅
范围：LawLink 内部使用，不商业化，不替换现有外部财务老师的报税职责

## 1. 决策摘要

采用“LawLink 业务财务 + 独立财务规则与对账层”的路线。

LawLink 继续作为客户、案件、委托收费、应收、确认收款、发票关联和律师业务分配的业务事实来源；新增财务域负责银行流水、外部账表、律所内部收入分配、个人结算、差异处理和后续正式会计凭证。

第一期不把现有 `FeeEntry` 改造成完整总账，也不直接引入 ERPNext、Dolibarr 或其他 GPL 系统的代码。第一期先完成可复核的规则核算和对账闭环，再根据外部财务老师确认的口径建设正式总账与三表。

## 2. 背景与边界

### 2.1 已有能力

LawLink 当前已经具备以下可复用能力：

- 客户、案件、承办团队和案件可见性；
- 委托收费、合同金额、分期应收和补充协议；
- 待确认实收、确认收款、付款分配和发票关联；
- 律师分成方案、分成计提、实际结算和财务更正；
- 审批、角色权限、审计日志和私有附件。

这些能力适合作为“案件/合同侧子账”。当前模型还没有完整的会计科目、借贷凭证、银行总账、工资社保账和正式三表，因此不能把现有财务页面直接当作外账会计系统。

### 2.2 本期目标

本期交付一个可重复运行、可解释、可追溯的内部核算与对账基础：

1. 导入银行流水、工资/社保资料和外部三表的结构化数据；
2. 将银行收款与 LawLink 已确认收款、发票、应收和案件关联；
3. 按版本化规则计算渠道佣金、律所留存、律师池、协办分成、报销和个人结算；
4. 对比银行流水、LawLink 收款、内部计算结果和外部财务账表，形成差异队列；
5. 输出可供内部复核的明细、汇总和 Excel/CSV 文件；
6. 所有计算结果能够追溯到原始批次、规则版本、操作者和调整记录。

### 2.3 明确不做

第一期不包含：

- 自动报税、税务申报或替代外部财务老师；
- 自动发放工资、社保缴费或对外付款；
- 自动读取或同步微信文档客户接单表；
- 正式会计凭证过账、期间结账和法定报表作为第一期的权威结果；
- OCR、银行开放接口或第三方支付接口；
- 将客户名称、合同号和案值复制到门户或日志中。

客户接单表在获得可控的 XLSX/CSV 导出后再设计字段映射，不阻塞第一期的规则计算与对账。

## 3. 方案选择

### 3.1 选定方案：LawLink 内置财务域

优点是最大程度复用现有律所业务模型、权限和审计链，案件收入不会被另一个系统重新录入；适合本所内部使用，数据边界也最容易控制。

代价是需要自行补充复式记账、工资社保和正式报表能力，因此必须将“案件子账”和“会计总账”分开设计。

### 3.2 备选方案：LawLink 对接 ERPNext

[ERPNext](https://github.com/frappe/erpnext) 已提供会计、现金流、项目、工时和盈利分析等 ERP 能力，适合作为未来正式会计后台。它采用 GPL-3.0，若采用，应作为独立服务通过 API 对接，不将其代码直接复制进 MIT 授权的 LawLink 仓库。代价是部署、数据同步、权限映射和双系统排错成本明显增加。

### 3.3 其他参考系统

[Dolibarr](https://github.com/Dolibarr/dolibarr) 有客户、报价、发票、订单、费用和会计模块，较轻量，但律师分成和案件生命周期仍需大量适配。

[LedgerSMB](https://github.com/ledgersmb/LedgerSMB) 的复式记账、发票、项目和 PostgreSQL 财务核心较强，但其技术栈和业务模型与 LawLink 差异较大。

[Akaunting](https://github.com/akaunting/akaunting) 的功能形态接近小型企业财务，但当前仓库标注 BSL，不按严格开源系统作为本项目的基础依赖。

## 4. 系统架构

### 4.1 模块边界

第一期仍使用 LawLink 的 Next.js 应用和 PostgreSQL，但财务新表、新服务和新页面按财务域隔离，不在案件页面散落计算逻辑。

```text
LawLink 业务域
  客户 / 案件 / 委托 / Billing / Receivable / FeeEntry / Payment
                         |
                         | 稳定业务 ID 与已确认事件
                         v
财务规则与对账域
  导入批次 -> 标准化流水 -> 匹配/差异 -> 分配计算 -> 复核快照 -> 导出
                         |
                         v
未来会计域
  科目 -> 凭证 -> 借贷分录 -> 期间结账 -> 三表
```

### 4.2 数据主权

- 案件、合同、案件应收和已确认案件收款仍以 LawLink 记录为准；
- 银行流水以导入批次和原始文件摘要为准，不覆盖原始文件；
- 规则计算结果是带版本的派生结果，不直接修改案件原始收款；
- 对账人工确认只能产生匹配关系或更正记录，不能删除原始流水；
- 未来正式会计凭证必须引用来源事件，不能绕过来源事件手工改余额。

### 4.3 关联键

第一期优先使用已有稳定 ID：`matterId`、`billingId`、`receivableId`、`feeEntryId`、`paymentId`、发票 ID 和导入批次/流水指纹。合同号、发票号和银行流水号只作为业务匹配字段，不能单独承担唯一身份。

## 5. 第一期开发表面

### 5.1 资料导入

新增导入批次管理，支持 XLSX、XLS、CSV；PDF 只作为附件留存，不作为第一期的自动入账来源。

每个批次保存：来源类型、文件摘要、账期、导入人、导入时间、行数、成功数、重复数和错误数。原始文件进入私有存储，日志和界面不输出完整身份证号、电话、银行卡号或客户敏感信息。

标准化流水至少包含：交易日期、金额、收支方向、对方摘要、用途摘要、账户标识、来源行号、原始批次和去重指纹。金额统一使用人民币分或 Decimal 规则处理，不使用浮点数。

### 5.2 对账工作台

匹配状态固定为：待匹配、系统建议、已确认、疑点、忽略。系统建议必须展示匹配依据，例如金额、日期窗口、发票、案件、合同和摘要；人工确认要记录操作者、时间和理由。

对账对象包括：

- 银行收款与 LawLink 已确认 `Payment`；
- 银行收款与发票/应收；
- 银行支出与费用、工资、社保、报销或合伙人往来；
- LawLink 收款与外部财务三表收入；
- 内部律师分配结果与实际支付/结算。

待确认的 LawLink 实收不能进入已收款对账结果，不能派生律师分成，沿用现有“先登记、后确认”的门禁。

### 5.3 规则计算器

规则由规则集、适用范围、生效日期、失效日期、比例、固定金额、舍入方式和说明组成。规则一旦被计算批次使用，不允许原地修改，只能建立新版本。

初始规则模板覆盖：

- 渠道案件：渠道佣金、律所留存、律师分配池；
- 自拓案件：按合伙人、独立律师等身份配置律所提取比例；
- 协办律师或助理的分配；
- 工资、社保、报销、预支、借款和个人税费预留；
- 合伙人出资、垫款和律所经营成本的独立归类。

流程资料中的 20%/45%/35%、10% 和 15%—18%只作为初始规则模板，必须可配置并保留生效日期与来源说明；25%等税务口径也只作为参数，不在系统中固化为法律结论。

计算结果至少分为三种视图：

1. 外部经营账：收入、成本、现金、应收、应付、出资和借款；
2. 律所内部经营分配账：案件收入在渠道、律所、承办人和协办人之间的分配；
3. 律师个人结算账：可分配收入、工资/社保、报销、预支、税费预留和应结余额。

每次计算生成不可变快照，显示输入金额、规则版本、每一步扣减、舍入余数和最终结果。默认舍入余数归入律所留存，同时在明细中显式展示；若实际制度不同，通过规则配置调整。

### 5.4 报表与导出

第一期报表是“核对报表”，不是法定报表，至少包括：

- 银行流水收支汇总；
- LawLink 收款、发票和应收汇总；
- 银行与 LawLink 的未匹配/金额差异；
- 按案件、律师、渠道和月份的内部分配；
- 工资、社保、报销、出资和垫款明细；
- 与外部三表的收入、成本和现金差异；
- 指定期间的规则计算快照和导出文件。

## 6. 权限、隐私与审计

- 读取财务明细、确认匹配、维护规则、确认更正和导出分别授权；
- 系统管理员身份不能自动取得业务财务确认权；沿用现有岗位与独立财务权限模型；
- 规则发布、导入、匹配确认、差异关闭、导出和更正都写入审计；
- 审计日志不得保存完整银行账号、身份证号、电话和客户原始敏感文本；
- 原始财务文件只存私有附件，下载继续使用短期授权链接；
- 任何测试、演示和 CI 数据使用合成样本，不把真实客户接单表、银行流水或工资表提交 Git。

## 7. 异常处理

- 文件无法识别、字段缺失或金额格式错误：批次失败并逐行给出原因，不产生部分正式结果；
- 重复导入：依据文件摘要和行指纹识别，保留重复记录的审计结果，不重复计算；
- 自动匹配不确定：进入疑点队列，不自动确认；
- 规则缺失、比例重叠、比例超过上限或生效期冲突：阻止整批计算，不输出半成品结算结果；
- 原始收款、流水和外部账表不一致：创建差异项，通过更正或补充来源解决，不直接改原始记录；
- 计算后规则变化：旧快照保持原规则版本，新规则只能重新生成新批次；
- 任何更正使用追加记录，禁止物理删除已经参与对账或结算的来源数据。

## 8. 验收标准

第一期达到以下条件才算完成：

1. 同一文件重复导入不会重复产生流水或分配结果；
2. 只有已确认的 LawLink 实收才能进入收款匹配和内部分配；
3. 每一笔分配都能回溯到案件、来源收款、规则版本和计算批次；
4. 所有差异都有状态、责任人、理由和关闭记录；
5. 规则变更不会改变历史计算快照；
6. 计算满足金额守恒、比例上限、非负余额和舍入可解释性；
7. 财务权限、敏感字段和私有文件下载通过正反向测试；
8. 使用合成样本完成银行流水、外部三表、案件收款和律师分配的端到端演练；
9. `npm run lint`、`npm run typecheck`、`npm run prisma:validate` 和 `npm run build` 通过；
10. 不执行生产数据库迁移、不导入真实客户接单表、不改变现有生产服务。

## 9. 后续阶段

第一期验收后，再单独设计正式会计域：会计科目、会计期间、凭证、借贷分录、工资社保、资产负债表、利润表和现金流量表。若外部财务老师要求使用成熟会计引擎，再评估通过 API 接入 ERPNext 或 LedgerSMB；该决策不提前绑定本期实现。
